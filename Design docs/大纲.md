## 1. 项目概述

### 1.1 项目名称

**NexusRPC** —— 支持MCP协议的高性能C++分布式RPC框架

### 1.2 项目定位

面向AI Agent时代的高性能服务通信基础设施。在提供传统RPC能力（服务注册发现、负载均衡、连接池、熔断限流）的基础上，原生集成MCP（Model Context Protocol）协议，使AI模型能够通过标准化接口，自动发现并调用分布式后端服务。

**目标形态**：开源可复用的中间件库 + 参考实现（examples），先满足单机 Demo 与内网小规模部署，暂不追求生产级 HA。

### 1.3 核心目标

| 目标 | 描述 | 衡量指标 |
|------|------|----------|
| 高性能RPC通信 | 基于Reactor模型的自研网络库 | 详见 §1.5 NFR |
| MCP协议原生支持 | 实现MCP Server SDK (C++版) | 兼容Claude Desktop等标准MCP客户端 |
| 分布式服务治理 | 服务注册发现、负载均衡、熔断限流 | 支持动态上下线，故障自愈 |
| AI工具注册中心 | 后端服务自动注册为AI可用工具 | 支持工具发现、Schema描述、动态调用 |

### 1.4 项目边界

**包含：**
- 自研高性能网络库（基于epoll）
- RPC核心：序列化、服务注册发现、负载均衡、连接池、熔断、限流
- MCP Server SDK：协议解析、工具注册、会话管理
- AI工具注册中心：工具元数据管理、Agent调用路由
- 基础运维能力：健康检查、优雅启停、指标暴露、结构化日志

**不包含（当前版本明确 out-of-scope）：**
- MCP Client SDK（使用现有客户端如 Claude Desktop、mcp-inspector 验证）
- MCP 授权框架（OAuth 2.1，2025-03-26 spec 引入），仅支持内网明文/共享密钥
- Sampling / Roots / Elicitation 等 MCP 高级能力（预留接口，不实现）
- 分布式事务
- 图形化管理界面
- 容器化部署编排（K8s Operator 等）
- 跨机房、多数据中心部署

### 1.5 非功能性需求（NFR）

| 指标 | 目标值 | 测量条件 |
|------|--------|----------|
| P99 延迟（Echo，本机 loopback） | < 1 ms | 单连接，1KB payload |
| P99 延迟（跨节点，千兆网） | < 5 ms | 1KB payload |
| 单节点最大并发连接 | ≥ 100,000 | 空闲长连接，Linux, 8C16G |
| 单节点 QPS（Echo） | ≥ 500,000 | 8 core, 1KB payload, 16 客户端连接 |
| 注册中心失联可用时长 | ≥ 5 min | 依赖本地缓存，超期后拒绝新调用 |
| 服务发现变更感知延迟 | < 1 s | 从服务注册到网关工具表更新 |
| 内存稳态 | 7×24h 无泄漏 | 通过 valgrind/ASan 长跑验证 |

**测试基线环境**：Linux x86_64，8 vCPU，16GB RAM，千兆内网。所有性能数字为参考值，最终以 benchmark 报告为准。

## 2. 总体架构设计

### 2.1 部署形态与进程边界

为降低早期实现复杂度，采用**"单进程多模块"**部署形态：

- **MCP Gateway 与 RPC Core 位于同一进程**，通过内存直接调用，不走网络。两者共用一份服务注册表本地缓存。
- **Service Registry（Redis）为独立外部依赖**，Gateway/Core 通过客户端连接。
- **Backend Service 为独立进程**，作为 RPC Server 使用 NexusRPC 的 Server SDK 注册到 Registry。Backend 之间也可作为 RPC Client 互相调用。
- 未来可通过配置切换为"Gateway 与 Core 独立进程"，届时两者通过内部 RPC 通信。

### 2.2 数据流

**流程1：AI Agent调用后端服务**
```
1. AI Agent (MCP Client) → [MCP Request] → MCP Gateway
2. MCP Gateway → 协议解析 → 提取 tool name + arguments
3. MCP Gateway → 查询本地工具注册表 → 命中 ServiceDescriptor
4. MCP Gateway → 参数校验（JSON Schema）→ 转为 RpcRequest
5. RPC Core → 服务发现 + 负载均衡 → 选中 Backend 实例
6. RPC Core → 连接池获取连接 → 发送 RpcRequest
7. Backend → 执行业务逻辑 → 返回 RpcResponse
8. RPC Core → 归还连接 → 返回结果给 Gateway
9. MCP Gateway → 结果转为 MCP tools/call result → 返回 AI Agent
```

**流程2：服务启动与注册**
```
1. Backend Service 启动 → 加载本地 .proto → 生成 ServiceDescriptor
2. Backend → 连接 Registry (Redis) → SET service:<name>:<instance-id> = meta（含 tools）
3. Backend → 启动心跳协程 → 每 5s EXPIRE 续约（TTL=15s）
4. Registry pub/sub 通道 service.change 广播变更
5. Gateway 订阅通道 → 更新本地工具注册表
6. Gateway → 通过 SSE / Streamable HTTP 向已连接 Agent 推送
                notifications/tools/list_changed
```

**流程3：服务下线**
```
优雅下线：Backend 主动 DEL 键 + PUBLISH 下线事件
异常下线：TTL 到期自动删除，Gateway 通过订阅感知（延迟 ≤ 15s）
```

## 3. 模块详细设计

### 3.1 网络传输层 (NexusNet)

#### 3.1.1 设计目标
- 基于epoll的边缘触发(ET)模式
- 支持10万+并发TCP连接
- 非阻塞IO + 异步事件回调

#### 3.1.2 核心类设计

```cpp
// 事件循环
class EventLoop {
public:
    void loop();  // 主循环
    void addChannel(Channel* ch);
    void updateChannel(Channel* ch);
    void removeChannel(Channel* ch);
    void runInLoop(std::function<void()> task);   // 跨线程投递
    void queueInLoop(std::function<void()> task); // 异步排队
private:
    int epollfd_;
    std::vector<struct epoll_event> events_;
    int wakeupFd_;  // eventfd，用于跨线程唤醒
};

// 抽象通道
class Channel {
public:
    void setReadCallback(ReadCallback cb);
    void setWriteCallback(WriteCallback cb);
    void enableReading();
    void enableWriting();
    void handleEvent();
private:
    int fd_;
    uint32_t events_;   // 关注的事件
    uint32_t revents_;  // 就绪的事件
    EventLoop* loop_;
};

// TCP服务器（主从Reactor多线程模型）
class TcpServer {
public:
    void start(int port, int threadNum = 4);
    void setConnectionCallback(ConnectionCallback cb);
    void setMessageCallback(MessageCallback cb);
private:
    EventLoop mainLoop_;              // 主线程，只负责accept
    std::vector<EventLoop*> subLoops_; // 工作线程，处理IO
    Acceptor acceptor_;
    std::unique_ptr<ThreadPool> threadPool_;
};
```

#### 3.1.3 线程模型
采用**主从Reactor + 线程池**模型：
- **主线程**：运行MainReactor，仅处理TCP连接建立
- **IO工作线程**：多个SubReactor，每个跑一个EventLoop，负责已建立连接的IO读写
- **业务线程池**：处理RPC方法调用等CPU密集型任务，避免阻塞IO线程

连接分发策略：Round-Robin 方式将新连接分配给 SubReactor。

### 3.2 MCP协议层

#### 3.2.1 MCP 版本与传输方式

**对齐规范版本**：`2025-03-26`（Streamable HTTP 引入版本）。同时兼容 `2024-11-05`（HTTP+SSE 旧模式）以支持早期客户端。

MCP 支持的传输方式：

| 传输方式 | 使用场景 | 本项目实现优先级 |
|---------|---------|-----------------|
| **stdio** | 本地进程通信，Claude Desktop 本机 MCP Server | P0（必做，实现成本低） |
| **Streamable HTTP** | 远程通信，单端点 `POST/GET /mcp` | P0（必做，新版客户端主流） |
| **HTTP + SSE**（legacy） | 兼容 2024-11-05 客户端，两个端点 | P2（可选，若时间允许） |

**授权**：本版本不实现 OAuth 2.1。生产部署建议置于反向代理后（Nginx + mTLS 或 Basic Auth）。

#### 3.2.2 支持的 MCP 能力

| 能力 | 状态 | 说明 |
|------|------|------|
| `initialize` / `initialized` | ✅ 必做 | 生命周期握手，能力协商 |
| `tools/list` | ✅ 必做 | 工具列表，从 Registry 动态生成 |
| `tools/call` | ✅ 必做 | 工具调用，路由至后端 RPC |
| `notifications/tools/list_changed` | ✅ 必做 | 服务上下线时广播 |
| `notifications/progress` | ✅ 必做 | 长任务进度上报 |
| `notifications/cancelled` | ✅ 必做 | 取消调用 |
| `ping` | ✅ 必做 | 保活 |
| `resources/*` | ⚠️ 预留接口 | 不实现，仅返回空列表 |
| `prompts/*` | ⚠️ 预留接口 | 不实现，仅返回空列表 |
| `sampling/*` | ❌ 不支持 | 需要 MCP Client 反向能力 |
| `roots/*`、`elicitation/*` | ❌ 不支持 | 超出当前范围 |

### 3.3 RPC核心层

#### 3.3.1 服务注册发现

```cpp
// 服务注册中心（基于Redis初版，后续可替换为etcd）
class ServiceRegistry {
public:
    bool registerService(const ServiceMeta& meta);
    std::vector<ServiceInstance> discover(const std::string& serviceName);
    void heartbeat(const std::string& serviceId);
    void watch(const std::string& serviceName,
               std::function<void(ServiceEvent)> callback);

private:
    std::unique_ptr<RedisClient> redis_;
    // 本地缓存：Registry 失联时降级使用（NFR: ≥5min 可用）
    std::unordered_map<std::string, std::vector<ServiceInstance>> cache_;
    std::chrono::steady_clock::time_point cacheStaleAt_;
};

// 服务元数据
struct ServiceMeta {
    std::string serviceId;       // UUID，实例级唯一
    std::string serviceName;
    std::string version;
    std::string host;
    int port;
    std::optional<std::vector<Tool>> tools; // AI 工具服务

    std::string serialize() const;
    static ServiceMeta deserialize(const std::string& data);
};
```

**Redis 数据模型**：

| Key 格式 | Value | TTL | 说明 |
|---------|-------|-----|------|
| `svc:{name}:{instanceId}` | JSON(ServiceMeta) | 15s | 实例注册信息，心跳续约 |
| `svc:{name}` (SET) | {instanceId...} | 无 | 快速列出所有实例 |
| `svc.change` (Pub/Sub) | JSON(event) | - | 上下线通知通道 |

**已知局限（Redis 方案）**：
- 主从异步复制存在数据丢失窗口，Failover 期间可能读到过时实例列表。
- 无原生 watch，靠 Pub/Sub + TTL，网络抖动可能误判下线。
- 后续版本考虑迁移至 etcd v3（Lease + Watch 语义天然更适合服务发现）。

#### 3.3.5 限流器

Server 端限流，采用**令牌桶**（平滑突发）+ 可选**滑动窗口**（严格计数）。粒度支持：
- 全局（进程级）
- 按服务方法（`service.method`）
- 按调用来源（clientId / MCP sessionId）

```cpp
class RateLimiter {
public:
    // 令牌桶：容量 capacity，每秒补充 rate 个令牌
    RateLimiter(double rate, double capacity);
    bool tryAcquire(uint32_t permits = 1);

private:
    std::atomic<double> tokens_;
    double rate_;
    double capacity_;
    std::chrono::steady_clock::time_point lastRefillAt_;
    std::mutex mutex_;
};
```

超限时 RPC 层返回错误码 `RATE_LIMITED (429)`，Gateway 层转换为 JSON-RPC 错误 `-32004`。

#### 3.3.6 超时与重试

| 层级 | 默认值 | 可配置项 |
|------|--------|---------|
| 连接建立超时 | 3s | `connect_timeout_ms` |
| 单次调用超时 | 5s | `call_timeout_ms`（支持按方法覆盖） |
| 最大重试次数 | 2 | `max_retries`（仅幂等方法，通过 proto option 标注） |
| 重试间隔 | 指数退避 100/300/900 ms | `retry_backoff_ms` |

调用方可通过 metadata（协议头 metadata 段）动态传递单次调用的 `deadline`、`retry` 覆盖默认配置。

#### 3.3.7 调用追踪

- 每个 MCP 请求进入时生成 `traceId`（16 字节，OpenTelemetry 兼容格式）。
- traceId 通过 RPC 协议头 metadata 段透传到下游服务。
- 日志、指标、错误响应均携带 traceId，便于关联。
- 预留 OpenTelemetry OTLP exporter 接口，但当前版本仅本地日志输出。

### 3.4 序列化层

**决策**：Body 部分**固定使用 Protobuf**，不做泛化模板。理由：
- 简化实现，避免运行时反射带来的复杂度。
- Protobuf 自身已足够高效，且 proto 文件即接口契约。
- JSON 序列化仅用于 MCP 层与 debug 日志。

```cpp
class ProtobufCodec {
public:
    static std::string encode(const google::protobuf::Message& msg);
    static bool decode(const std::string& data, google::protobuf::Message* msg);
};
```

#### 3.4.1 协议头设计（v1）

采用固定长度头 + 变长 metadata + 变长 body 三段式：

```cpp
struct RpcHeader {
    uint32_t magic;          // 0x4E525043 "NRPC"
    uint8_t  version;        // 协议版本，当前为 1
    uint8_t  msgType;        // 0=Request 1=Response 2=StreamData 3=StreamEnd 4=Ping 5=Pong
    uint8_t  compressType;   // 0=none 1=snappy 2=zstd
    uint8_t  serializeType;  // 0=protobuf 1=json（保留）
    uint32_t totalLength;    // 包含头在内的总字节数
    uint64_t requestId;      // 64位，支持异步/流式匹配
    uint32_t metaLength;     // metadata 段长度（用于 traceId、deadline、tenant 等）
    uint32_t bodyLength;     // body 段长度
    // 4 bytes reserved
} __attribute__((packed));   // 固定 32 字节
```

**字段说明**：
- `metadata` 段为 KV 列表（Protobuf `map<string,string>`），承载横切关注点。
- `requestId` 从 64 位随机数生成，避免回卷。
- `msgType = 2/3` 支持未来引入 Server Streaming（当前版本可预留不实现）。

### 4.2 MCP ↔ RPC 映射规则

本项目最核心的设计点：**将 Protobuf 服务方法自动暴露为 MCP 工具**。映射规则如下：

| RPC 概念 | MCP 概念 | 映射规则 |
|---------|---------|---------|
| `Service.Method` (`is_tool=true`) | `Tool` | `name = service_name.method_name`，snake_case |
| Method 的 request 消息 | `Tool.inputSchema` | Protobuf FieldDescriptor → JSON Schema（见 §4.4） |
| Method 的 response 消息 | `Tool.call` 结果 | 转 JSON 后放入 `content[0].text`（string）或 `content[0].data`（结构化） |
| Method 错误 (`RpcResponse.error_code`) | JSON-RPC `error` | 见 §4.3 错误码映射表 |
| Method proto option `description` | `Tool.description` | 从自定义 option `(nexus.description)` 读取 |
| Service 上线（Registry 事件） | `notifications/tools/list_changed` | Gateway 订阅 Redis pub/sub 后广播 |
| Method proto option `idempotent` | 客户端可重试提示 | 仅内部使用，不暴露给 Agent |
| 长任务进度回调 | `notifications/progress` | Backend 通过 metadata 上报，Gateway 透传 |
| Agent 取消请求 | RPC deadline / 主动关闭 | `notifications/cancelled` → 转 RPC 层取消 |

### 4.3 错误码规范

**RPC 内部错误码**（`RpcResponse.error_code`）：

| Code | 名称 | 含义 |
|------|------|------|
| 0 | OK | 成功 |
| 1 | UNKNOWN | 未分类错误 |
| 2 | INVALID_ARGUMENT | 参数校验失败 |
| 3 | DEADLINE_EXCEEDED | 超时 |
| 4 | NOT_FOUND | 服务/方法不存在 |
| 5 | UNAVAILABLE | 目标服务不可用（无实例/熔断） |
| 6 | INTERNAL | 服务端内部错误 |
| 7 | RATE_LIMITED | 触发限流 |
| 8 | CANCELLED | 客户端取消 |

**JSON-RPC / MCP 错误码**（`Error.code`）：

| Code | 类型 | 说明 | 对应 RPC Code |
|------|------|------|--------------|
| -32700 | ParseError | JSON 解析失败 | - |
| -32600 | InvalidRequest | 不符合 JSON-RPC 规范 | - |
| -32601 | MethodNotFound | MCP 方法不存在 | 4 |
| -32602 | InvalidParams | 参数校验失败 | 2 |
| -32603 | InternalError | 内部错误 | 1, 6 |
| -32001 | ToolNotFound | 工具未注册（自定义） | 4 |
| -32002 | ToolExecutionError | 后端调用失败（自定义） | 5, 6 |
| -32003 | Timeout | 调用超时（自定义） | 3 |
| -32004 | RateLimited | 限流（自定义） | 7 |
| -32005 | Cancelled | 已取消（自定义） | 8 |

### 4.4 Protobuf → JSON Schema 转换

```cpp
// 将 Protobuf MethodDescriptor 转换为 JSON Schema
json ProtobufToJsonSchema(const google::protobuf::Descriptor* input) {
    json schema;
    schema["type"] = "object";
    schema["properties"] = json::object();
    json required = json::array();

    for (int i = 0; i < input->field_count(); i++) {
        const auto* field = input->field(i);
        json fieldSchema;

        // 从自定义 option 读取描述
        if (field->options().HasExtension(nexus::description)) {
            fieldSchema["description"] =
                field->options().GetExtension(nexus::description);
        }

        switch (field->type()) {
            case FieldDescriptor::TYPE_STRING: fieldSchema["type"] = "string"; break;
            case FieldDescriptor::TYPE_INT32:
            case FieldDescriptor::TYPE_INT64:
            case FieldDescriptor::TYPE_UINT32:
            case FieldDescriptor::TYPE_UINT64: fieldSchema["type"] = "integer"; break;
            case FieldDescriptor::TYPE_DOUBLE:
            case FieldDescriptor::TYPE_FLOAT:  fieldSchema["type"] = "number"; break;
            case FieldDescriptor::TYPE_BOOL:   fieldSchema["type"] = "boolean"; break;
            case FieldDescriptor::TYPE_ENUM: {
                fieldSchema["type"] = "string";
                json enumValues = json::array();
                for (int j = 0; j < field->enum_type()->value_count(); j++) {
                    enumValues.push_back(field->enum_type()->value(j)->name());
                }
                fieldSchema["enum"] = enumValues;
                break;
            }
            case FieldDescriptor::TYPE_MESSAGE:
                fieldSchema = ProtobufToJsonSchema(field->message_type());
                break;
            default: fieldSchema["type"] = "string"; // fallback
        }

        if (field->is_repeated()) {
            json arraySchema;
            arraySchema["type"] = "array";
            arraySchema["items"] = fieldSchema;
            fieldSchema = arraySchema;
        }

        schema["properties"][field->name()] = fieldSchema;
        if (field->is_required()) required.push_back(field->name());
    }

    if (!required.empty()) schema["required"] = required;
    return schema;
}
```

## 9. 待决策事项（Open Questions）

以下事项在进入第0阶段前需要明确：

1. **依赖管理方式**：FetchContent（简单，编译慢）vs vcpkg（复杂，缓存友好）。
2. **codegen 策略**：手写 Stub vs Protobuf 插件生成。建议 v1 手写，v2 引入插件。
3. **是否支持流式 RPC**：如果 v1 支持，MCP `notifications/progress` 实现更自然；如果不支持，需在网关层用 pending call 表模拟。
4. **配置文件格式**：YAML（可读性好）vs TOML（解析简单）vs 纯 JSON。
5. **注册中心后续演进**：v2 是否迁移 etcd？如果是，Registry 抽象层需要在 v1 就设计好。
